# 0063 · The compiler owns the String Catalog

**Date:** 2026-09-05 · **Item:** HL-046 · **Status:** decided

## Context

HL-046 asked for two lint rules: fail when a `LocalizedStringKey` literal has no
catalog entry, and when a bare literal reaches `Text(variable)` through a struct
property. Both were written, and both work. Writing them turned up why the gap
existed at all, and the answer made them the second-best half of the fix.

`SWIFT_EMIT_LOC_STRINGS` was **NO** on the app and widget targets. Xcode sets it
when a String Catalog is added through its own UI; this project's `.xcodeproj` is
generated by xcodegen from `project.yml`, which never named the setting, so the
compiler extracted nothing and the catalogs sat at `extractionState: manual` with
nothing on earth reconciling them against the source.

Everything HL-046 describes follows from that one line. Three items — HL-006,
HL-007, HL-008 — each said localization was done, and none of them could have
known otherwise: no gate compared the catalog to the code, and the app had never
been launched in a language whose absence would show.

## What the gap actually held

Turning the setting on and running `xcodebuild -exportLocalizations` produced the
measurement, which is worse than the item's estimate of twenty-one:

- **53 keys the code needs and the catalogs did not carry.** Every one of them
  fell back to English in eight locales.
- **16 of those replaced a near-miss the catalog already had** — a hand-authored
  key that had therefore *never once resolved*: `%@` where the code passes an
  integer (`Contraction %@, lasted %@, at %@`), a dropped leading space, a
  trailing space, a copy edit the key was never updated for (`under the ?` after
  the copy became `under the question mark`).
- **Four Japanese, Korean and Chinese translations reordered their arguments
  without positional specifiers.** `printf` consumes arguments in written order,
  so those printed the contraction *count* where the *interval* belonged — and
  with `%lld` now correctly in the mix, one of them would have read an integer
  out of a pointer.

A Spanish screenshot of the fixed History screen then found the last of it: the
mono-caps instrument band, `THIS STRETCH · AVG 5:00 APART · 1:02 LONG · OVER
1 H 5 M`, still in English. Mono-caps vocabulary carries no lowercase letter, so
the textual lint's prose test could never see it, and the strings were plain
`String`s that no extractor could either.

## Decision

**The compiler is the authority on what the catalogs must contain, and a gate
enforces that they match it.**

1. `SWIFT_EMIT_LOC_STRINGS: YES` in `project.yml`, project-wide.
2. Every entry loses `extractionState: manual`, so an entry no code path produces
   is marked `stale` by the next export instead of living on unseen.
3. `scripts/lint-loc-catalog.sh` runs the export and fails if the catalogs
   changed — a key added means one is missing from the catalog, a key marked
   stale means the catalog carries one nothing produces. It restores the files
   either way, so a gate run never modifies the tree. `gate.sh` calls it, and so
   does CI's macOS tier.
4. `scripts/apply-language.py` learns positional specifiers: `%N$lld` is
   understood, the indices must be a permutation of English's arguments, and the
   type at each index must match English's type there. A translation that
   reorders now has to say so.

**The textual rules stay, and are not redundant.** `lint-localizable.sh` runs on
ubuntu on every push, where no Xcode exists; the extraction gate needs a macOS
runner and bills at the 10x multiplier, so it runs on the manual tier and in the
local gate. Two of the three new textual rules also cover shapes the compiler
cannot: a literal written into a `String`-typed struct property is a *verbatim*
string by the time `Text` renders it, and mono-caps instrument vocabulary is a
plain `String` the extractor is right not to see.

## Why not just trust the extractor

Because it is silent about the two shapes that produced this item's own examples.
`LegRow(label: "APART")` compiles, extracts nothing, and renders English forever;
the compiler's only signal is a "non-literal key" warning at the far-away
`Text(row.label)` call, which is not the site to fix. And `"THIS STRETCH · AVG
\(x) APART"` is a `String`, correctly invisible to a tool that looks for
localizable literals. A gate made only of the extractor would have passed the
tree that shipped, twice.

## Consequences

- Adding a user-facing string is now a two-step loop with a gate on the end: write
  it, run the export, translate the key it produced through `docs/i18n/maps`.
- The catalogs are 255 keys × 9 locales with no gaps, and a re-export is a
  fixed point.
- `CHECK` now carries each language's own flag word (`REVISAR`, `要確認`,
  `待核对`), which decision 0062 already required of this vocabulary and which
  the sweep dialog's copy was restated to match.
- Spanish is verified by `verify-language.py` like the other eight: its
  `neverSays` list was mirrored out of `VerifiedLanguages` into `es-app.py`,
  where the pipeline can read it.
- One named limit, in the rule's own doc comment: the mono-caps rule tests for an
  all-caps word of two or more letters plus a space, so a single-letter unit —
  `"\(hours) H \(minutes) M"` as it was written before this item — is not caught
  by it. That literal is localized now; the next one like it will need the same
  Spanish-screenshot look this item ended with.
